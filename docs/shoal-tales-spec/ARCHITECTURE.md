# Shoal Tales — Implementation Architecture for Roleplay Hub

Decisions locked in with the user: **full port** (build toward the complete design bible, not an MVP slice), **separate files** (don't fold into the single `index.html`/`server.js`).

## File layout

New top-level directory `shoal-tales/` (served as static files by the existing `server.js` static file handler — no new server plumbing needed for serving them):

| File | Role |
|---|---|
| `shoal-tales/data.js` | Static game data generated from `docs/shoal-tales-spec/*.csv` — junk, curios, fish, Collector's Sets, decorations, bottle letters. Plain `<script>`, assigns `window.ShoalTalesData`. No build step: hand-authored or regenerated by a one-off local script when the CSVs change, not compiled at request time. |
| `shoal-tales/engine.js` | Pure, framework-free game-logic functions: the dredge timer formula, sort value formula, Emporium drink payout, retire-goal lookups, bonus-stacking resolution, etc. — straight ports of the formulas in `docs/shoal-tales-spec/`. Assigns `window.ShoalTalesEngine`. Used by BOTH the client (for instant UI feedback) and the server (as the authoritative calculation — see RNG note below), by `require()`-ing the same file from Node (it's plain ES5-compatible JS with no browser globals) and `<script>`-including it in the browser. |
| `shoal-tales/ui.js` | React components: `ShoalTalesScreen` and its sub-screens (Boat/Dredge, Sort Tray, Collector's Log, Town, each Emporium room, Shipwright, Social, Settings). Same `React.createElement` hand-written convention as `index.html`. Assigns `window.ShoalTalesUI.ShoalTalesScreen`. |
| `shoal-tales/style.css` | Shoal Tales' own nautical visual theme — deliberately NOT tied to a World's Visual Theme, since Shoal Tales is an account-level feature, not World-scoped (see Nav integration below). |

`index.html` changes: add `<script src="shoal-tales/data.js">`, `<script src="shoal-tales/engine.js">`, `<script src="shoal-tales/ui.js">` after the React/ReactDOM CDN tags and before the main inline `<script>` (so `window.ShoalTalesUI` etc. exist when `App` is defined), plus a `<link rel="stylesheet" href="shoal-tales/style.css">`.

## Why server-authoritative RNG

The design bible's Minecraft version runs entirely server-side already (it's a Minecraft server plugin). Nothing in the spec says client vs. server for the web port, but it's an economy game with persistent value (coins, rare collectibles) — so every RNG roll that affects payout (haul contents, curio rarity, puzzle box prizes, customer drink orders, crate contents) MUST be rolled server-side, in `server.js`, using `shoal-tales/engine.js`'s pure functions. The client sends an action ("drop the dredge," "sort this tray item into bin X"), the server computes the real outcome and the real value, and broadcasts/returns it. This is a departure from nothing in the spec (the spec doesn't discuss client/server split at all, being written for a server-authoritative Minecraft plugin) but is a necessary adaptation flagged explicitly here rather than discovered as a bug later.

## Data model — `db.shoalTalesSaves` (server.js, new top-level `db` collection)

One record per account handle, mirroring the existing `db.users`/`db.worlds` keyed-object pattern. Persisted through the same dual JSON-file/Postgres mechanism already in `server.js` — no new persistence code needed, just adding `shoalTalesSaves: {}` to `defaultDb` and the load/save paths (4 places in server.js currently enumerate every top-level collection; this needs to be added to the same 4 spots: `defaultDb`, `loadDatabaseFromFile`, `initializeDatabase`'s PG restore, and nowhere else — `saveDatabaseSync` already serializes the whole `db` object generically).

Shape mirrors the Reset vs. Kept-for-good split from `11-retiring.md` directly — run-scoped fields reset on retire, the rest persist. Exact field list will firm up per-phase (tasks 16-25) rather than being fully pre-specified here, to avoid designing fields for systems not yet built. Starting shape:

```js
shoalTalesSaves: {
  '@handle': {
    handle, createdAt,
    coins, lifetimeCoinsThisRun, tray, basketLevel, winchLevel, brushLevel, charmLevel,
    stationsInstalled, stationHiddenCounters, cooler, storedJunk, sortedGoods, supplies,
    streak, bestStreakThisRun, depth, area,
    storyProgress, standingOrdersProgress, dailyProgress,
    // kept for good:
    collectorsLog, magicCurios, creaturesSeen, goldenLog, storedCurios, rareMaterials,
    emporium, retirements, title, featTitleChosen, unlockedAreas, unlockedDepths,
    looks, equippedLooks, bottleLettersFound, bottleLettersWritten, settings, allTimeStats, questBookProgress
  }
}
```

## API endpoints (`server.js`), all under `/api/shoal-tales/*`

Following the existing route style (`if (reqPath === '...' && req.method === '...')` blocks). Built incrementally per phase:
- Phase (core loop, task 17): `GET /save`, `POST /dredge`, `POST /sort`, `POST /sell`, `POST /upgrade`, `POST /station/install`
- Phase (Emporium, task 21): `POST /emporium/open`, `/emporium/counter-serve`, `/emporium/puzzle-solve`, `/emporium/prize-box`, `/emporium/work-order-fill`, `/emporium/decoration-place`, `/emporium/tip-collect`, `/emporium/away-earnings-collect`
- Phase (Retiring, task 22): `POST /retire`
- Phase (Cosmetics, task 23): `POST /cosmetics/equip`, `/cosmetics/try-on`
- Phase (Social, task 24): party/guild/visit/gift/bottle-letter endpoints, needing new `db` collections (`shoalTalesParties`, `shoalTalesGuilds`, player-written letters) and new WebSocket broadcast types (`SHOAL_RETIREMENT`, `SHOAL_GUILD_QUEST_UPDATED`, `SHOAL_LETTER_FOUND`, etc.), following the existing `WORLD_*`/`NEW_DM` broadcast pattern.

## Nav integration (task 26, done last)

- Bottom nav tab array lives at `index.html` ~line 9403 (`App` component, the 5-entry array mapped into `<nav>` buttons). Add a 6th entry: `{ id: 'shoal', label: 'Shoal Tales', icon: Icons.Anchor }`.
- New `Icons.Anchor` SVG needed in `IconsRaw` (~line 1023) — none of the existing icons fit a nautical/game tab. (The `Icons` Proxy already falls back to a generic circle for any missing name, so nothing breaks if this is added later, but a proper icon is cheap and worth doing now.)
- Main render: add `activeTab === 'shoal' && React.createElement(ShoalTalesUI.ShoalTalesScreen, { userProfile, ... })` alongside the existing `activeTab === 'cast'`/`'settings'` branches (~line 9251 area).
- Unlike Chat/Wiki/Cast, Shoal Tales is **account-level, not World-scoped** — `ShoalTalesScreen` doesn't need `activeWorld`/`activeChannelId`/World permissions at all, just the logged-in `userProfile.handle`. This meaningfully simplifies integration versus the rest of the app's World-centric design.
- Tab badge: a small indicator (e.g. "away earnings ready to collect," "daily request available") could reuse the existing unread-dot pattern on the nav icon (`t.id === 'shoal' && ... && <span className="...dot..."/>`), deferred to whichever phase makes it relevant.

## Testing approach
Reuse the two established patterns from this codebase's history: (1) `vm.runInContext`-based offline component tests against `shoal-tales/ui.js` + `shoal-tales/data.js` + `shoal-tales/engine.js`, mocking React/window/etc.; (2) live-server integration tests against the real `server.js` (temp `DATA_DIR`, fixed port, real HTTP) for every new `/api/shoal-tales/*` endpoint, verifying server-authoritative RNG/value calculations match `engine.js` exactly.
